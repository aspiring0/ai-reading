# 14 - Redis 缓存：为什么要缓存、怎么缓存

## 一句话说清楚

缓存 = 把常用的数据放内存里，下次用直接拿，不用再去数据库查。就像把常用电话号码存手机通讯录，不用每次翻电话本。

## 为什么需要缓存

```
没有缓存：
  用户请求 → 后端 → 查数据库（慢，要 50ms） → 返回
  用户请求 → 后端 → 查数据库（又查一遍？50ms） → 返回

有缓存：
  第 1 次请求 → 后端 → 查数据库（50ms） → 存到 Redis → 返回
  第 2 次请求 → 后端 → 查 Redis（2ms）→ 直接返回！快 25 倍
```

Redis 是纯内存数据库，读写的速度比 PostgreSQL 快很多。适合存"经常读但不常改"的数据。

## Cache-Aside 模式（我们用的）

```
读文章详情时的流程：
                    ┌─────────┐
                    │ Redis 有？│
                    └────┬────┘
                    有 ↓      ↓ 没有
              直接返回    ┌──────────┐
                         │ 查数据库  │
                         └────┬─────┘
                              ↓
                         ┌──────────┐
                         │ 写入 Redis│ ← 下次就能命中了
                         └────┬─────┘
                              ↓
                           返回

更新/删除文章时：
  改数据库 → 删 Redis 缓存 → 下次读自然拿最新的
```

## 为什么用"删除"而不是"更新"缓存

```
❌ 更新缓存的坑（并发问题）：
  用户 A 正在改标题 → "新标题"
  用户 B 同时在读   → 还是"旧标题"
  A 改完了 → 更新缓存为"新标题"
  B 的旧请求到了 → 把缓存改回"旧标题"
  → 数据库是新的，缓存是旧的，不一致了！

✅ 删除缓存（简单安全）：
  改数据库 → 直接删缓存
  下次有人读 → 缓存没有 → 从数据库拿最新的 → 写入缓存
  → 永远不会出现不一致
```

## 代码在哪里

| 文件 | 作用 |

| `services/article_service.py` | 业务层调用缓存：读时穿透、改时失效 |

## 缓存的 TTL（过期时间）

我们设了 1 小时（3600 秒）。即使缓存和数据库不一致，最多 1 小时后缓存自动过期，下次读就拿新的。

所以：改数据时主动删缓存（保证即时生效） + TTL 兜底（防止漏删）。
